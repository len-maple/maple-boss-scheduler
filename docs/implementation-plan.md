# メイプルストーリー ボススケジューラー 実装計画書

作成日: 2026-08-21

## 1. 概要

メイプルストーリー（MMORPG）のボス討伐に向けて、パーティーリーダーが候補日程を発行し、
メンバーが各候補日の参加可否を入力、リーダーが集計して開催日時を確定する
Webスケジュール調整ツール。GitHub Pages（`*.github.io`）で公開する。

## 2. ユーザーロール

| ロール | できること |
|---|---|
| リーダー | スケジュール（候補日程）の発行、メンバー入力状況の確認、開催日時の確定 |
| メンバー | 発行されたスケジュールへのアクセス、各候補日への回答（○/△/×）入力 |

## 3. 機能要件

### 3.1 スケジュール発行（リーダー）

- タイトル（例:「ゼムラ討伐」）と候補日を複数登録して発行
- 発行すると共有用URL（＋スケジュールID）が生成され、メンバーはそのURLからアクセスする
- ログイン不要（リーダー識別のみ簡易的に必要、詳細は §8 未決定事項）

### 3.2 メンバー入力

- 共有URLにアクセスし、名前を入力（初回のみ）
- 候補日ごとに以下のいずれかを選択
  - **○**：終日参加可能
  - **△**：特定時間帯のみ参加可能（→ §3.3 の詳細UIへ）
  - **×**：参加不可

### 3.3 △入力時のUI詳細（30分刻み時間選択）

- 対象日を選択すると、00:00〜24:00 を **30分単位・48コマ** のグリッドで表示
- 各コマは「クリックで参加可能としてトグル」する押しボタン式（テキスト入力はしない）
- 48コマを1つずつクリックするのは手間が大きいため、**長押し（ドラッグ）で連続選択**できるようにする
  - PC: `mousedown` したコマから `mousemove` で通過したコマを連続してON/OFFにする（ペイント方式）
  - スマホ: `touchstart` → `touchmove` で同様のドラッグ選択に対応（誤スクロール防止のため `touch-action: none` 等を検討）
  - 単発クリック（ドラッグなし）は1コマだけのトグルとして機能させる
  - 補助操作として「全選択」「全解除」ボタンも用意する

### 3.4 集計・確定（リーダー）

- 候補日 × メンバーのマトリクス表示で入力状況を一覧化（○△×が色分けされたテーブル）
- △の日はどの時間帯に何人参加できるかが分かるよう、時間帯ごとの参加可能人数もあわせて可視化（ヒートマップ的な表示）
- リーダーが最終的に「○月○日 ○時○分開始」を指定して確定
- 確定後はメンバーもその日時を確認できる画面に切り替わる

### 3.5 自分が参加した確定済みスケジュールの一覧表示（発行ページ）

- スケジュール発行ページ（トップ画面）に、**自分が過去に回答したスケジュールのうち、日程が確定（`status: "confirmed"`）済みのもの**を一覧表示する
- 一覧には「タイトル」「確定日時」を表示し、クリックで §3.4 の確定結果画面（詳細）に遷移できるようにする
- 「自分」の識別はログイン機能を設けない前提のため、ブラウザの `localStorage` に「回答したスケジュールID一覧」を保存しておき、発行ページ表示時にそのIDのスケジュールをまとめて取得して `confirmed` のものだけ絞り込む方式とする（§5 参照）
  - この方式では**同一ブラウザ・同一端末でのみ**一覧が表示される（別端末からは見えない）。端末をまたいで見たい場合は将来的にログイン機能の追加が必要（§8 未決定事項）

## 4. 技術スタック（案）

GitHub Pagesは静的ファイルしか配信できないため、複数人でデータを共有するには
何らかのBaaS（バックエンド機能付きサービス）が必要になる。

| 分類 | 案 | 理由 |
|---|---|---|
| フロントエンド | React + TypeScript + Vite | GitHub Actionsでビルド→Pagesへデプロイしやすい |
| スタイリング | Tailwind CSS | グリッドUIやテーブルの実装が速い |
| データ共有 | Firebase Firestore | 無料枠あり、サーバー不要でクライアントから直接読み書き可能、GitHub Pagesとの組み合わせの定番 |
| 認証 | リーダーのみ簡易認証（匿名 or Googleログイン）、メンバーはURL＋名前入力でログイン不要 | 身内利用のツールのため、手軽さを優先 |
| ホスティング/CI | GitHub Pages + GitHub Actions | 要件どおり `github.io` で公開 |

## 5. データモデル（Firestore想定）

```
schedules/{scheduleId}
  ├ title: string
  ├ leaderId: string
  ├ candidateDates: string[]        // 例: ["2026-09-05", "2026-09-06"]
  ├ status: "collecting" | "confirmed"
  ├ confirmedDate: string | null
  ├ confirmedTime: string | null    // 例: "21:00"
  └ createdAt: timestamp

schedules/{scheduleId}/responses/{memberId}
  ├ memberName: string
  ├ answers: {
  │    "2026-09-05": { type: "circle" | "triangle" | "cross", slots?: number[] }
  │    // slots は type が triangle の場合のみ、00:00始まりの30分コマ index(0-47) の配列
  │ }
  └ updatedAt: timestamp
```

### 5.1 クライアント側ローカルデータ（§3.5 用）

Firestoreに加えて、ブラウザの `localStorage` に以下のような形式で
「自分が回答したスケジュール」を記録し、発行ページでの一覧表示に使う。

```
localStorage["myScheduleIds"] = [
  { "scheduleId": "abc123", "memberId": "xxxx" },
  { "scheduleId": "def456", "memberId": "yyyy" }
]
```

- メンバーがスケジュールに回答（§3.2）した際にこのリストへ追記する
- 発行ページ表示時にリスト内の各 `scheduleId` を Firestore から取得し、`status === "confirmed"` のものだけ抽出して表示する

## 6. 画面一覧

1. **スケジュール発行ページ**（トップ画面）: 新規スケジュール作成フォーム＋自分が参加し確定済みのスケジュール一覧（§3.5）
2. **スケジュール入力画面**（メンバー）: 名前入力 → 候補日ごとに○/△/×選択、△選択時は30分グリッドをモーダル表示
3. **集計・確認画面**（リーダー）: 候補日×メンバーの一覧表示、時間帯別の参加可能人数、開催日時確定フォーム
4. **確定結果画面**（全員）: 確定した日時の表示

## 7. 実装フェーズ

| フェーズ | 内容 |
|---|---|
| Phase 0 | 環境構築（Vite + React + TS、Firebaseプロジェクト作成、GitHub Actions設定）。Firebase側の手作業は [firebase-setup.md](./firebase-setup.md) を参照 |
| Phase 1 | スケジュール作成・URL発行機能 |
| Phase 2 | メンバー入力画面（○/×の基本入力） |
| Phase 3 | △用30分刻みグリッドUI（クリック＋ドラッグ/長押し連続選択） |
| Phase 4 | 集計画面・開催日時確定機能 |
| Phase 5 | レスポンシブ対応（スマホ操作を想定したスタイリング調整） |
| Phase 6 | 発行ページへの「自分が参加した確定済みスケジュール一覧」表示（§3.5） |
| Phase 7 | 動作確認・GitHub Pagesへの公開（リポジトリの Settings > Pages > Source を「GitHub Actions」に設定し、`main` へのpushで自動デプロイ） |

## 8. 未決定事項・確認したいこと

- メンバーの識別を「名前入力のみ」で許容するか、簡易パスワード等を設けるか
- 候補日の最大数、パーティー人数の上限（UI設計・Firestore読み取り量に影響）
- リーダーがメンバーの入力状況をリアルタイムで見たいか、それとも手動更新で十分か
- 確定時にDiscord/LINEなどへの通知連携が必要か（将来拡張として切り出すか）
- 主な利用デバイスはスマホ想定かPC想定か（UIの優先度に影響）
- §3.5の「自分の確定済みスケジュール一覧」について、`localStorage`ベース（同一端末限定）で許容するか、将来的にログイン機能を入れて端末をまたいで同期できるようにするか
